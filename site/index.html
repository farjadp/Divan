Divan

A product team of AI agents —
built around one human who decides.

A drop-in kit for Claude Code: seven specialised roles, three approval gates, and an owner who decides what to build, what to cut, and when it is good enough.

View on GitHub Install The method

Status: early (v0.1). Divan has been installed and adapted on one live product (case study). A full feature loop — idea to release — has not yet been run end to end. Results, including failures, will be published when it has.

The problem

AI coding agents are fast. Speed is not the problem. The problem is that a single agent asked to "build the feature" acts as product manager, architect, developer and reviewer at once — and grades its own work. Human teams solved this long ago with separate roles and approval points. Divan brings that structure to agents.

The team

spec-writer
Product manager — Feature Definition
does not edit code
architect
Tech lead — design, three variants, task breakdown
does not edit code
builder
Full-stack and mobile developer, one task at a time
edits code
reviewer
Senior engineer and QA — independent of the builder
reports only
security-checker
Security and privacy — checks your public promises
reports only
feature-engineer
ML engineer — model input features, only if you have a model
ML folder only
release-docs
DevOps and technical writer — prepares, never deploys
docs only

The loop

  1. Gate A — scope. You approve the feature card, including what was cut.
  2. Gate B — design. You approve the approach and pick one of three variants.
  3. Gate C — release. You merge, deploy and publish. Agents never do.

Install

git clone --depth 1 https://github.com/farjadp/divan.git
./divan/install.sh /path/to/your/project

The installer never overwrites a file. Then fill in CLAUDE.md, open the project in Claude Code, and say: "adapt Divan to this repo" for an existing project, or "run the feature loop for: <one small, real feature>".

Three facts every agent must know

Most agent-team failures are not coding mistakes. They are an agent breaking one of these, because nobody wrote it down.

1. What triggers a production deploy? If pushing to main deploys, an agent pushing is a release.
2. What is the tracking policy? It decides how success can be measured. Divan never adds tracking to a product that promises none.
3. What does the product publicly promise? The security agent checks every change against each promise by name.

Why "Divan"?

In historical Persian government, the divan was the administration: specialised departments — correspondence, finance, the army register — each doing one job well, all answering to one decision-maker. That is the shape of this team.

مسئله

ایجنت‌های کدنویس سریع‌اند. مشکل سرعت نیست. مشکل این است که وقتی به یک ایجنت می‌گویی «این فیچر را بساز»، هم‌زمان مدیر محصول، معمار، برنامه‌نویس و بازبین می‌شود و کار خودش را خودش نمره می‌دهد. تیم‌های انسانی این مشکل را با نقش‌های جدا و نقطه‌های تأیید حل کرده‌اند. دیوان همین ساختار را برای ایجنت‌ها می‌آورد.

چرخهٔ کار

  1. دروازهٔ A — محدوده. تو کارت فیچر را تأیید می‌کنی، از جمله چیزهایی که حذف شده.
  2. دروازهٔ B — طراحی. تو روش را تأیید می‌کنی و یکی از سه نسخه را انتخاب می‌کنی.
  3. دروازهٔ C — انتشار. تو merge، deploy و منتشر می‌کنی. ایجنت‌ها هرگز.

سه واقعیتی که هر ایجنت باید بداند

بیشتر شکست‌های تیم‌های ایجنتی اشتباه کدنویسی نیستند. ایجنتی یکی از این سه را شکسته، چون کسی آن را ننوشته بود.

۱. چه چیزی باعث انتشار می‌شود؟ اگر push روی main یعنی انتشار، پس push کردن ایجنت یعنی انتشار.
۲. سیاست ردیابی چیست؟ این تعیین می‌کند موفقیت چطور سنجیده شود. دیوان هرگز به محصولی که قول «بدون ردیابی» داده، ردیاب اضافه نمی‌کند.
۳. محصول چه قول‌هایی داده است؟ ایجنت امنیت هر تغییر را با تک‌تک این قول‌ها چک می‌کند.

چرا «دیوان»؟

در حکومت‌های تاریخی ایران، «دیوان» همان دستگاه اداری بود: واحدهای تخصصی مثل دیوان رسائل، دیوان استیفا و دیوان عرض. هر واحد یک کار را خوب انجام می‌داد و همه به یک تصمیم‌گیرنده پاسخ می‌دادند. این تیم هم همین شکل را دارد.

وكلاء البرمجة سريعون، والسرعة ليست المشكلة. المشكلة أن الوكيل الواحد، حين يُطلب منه «ابنِ هذه الميزة»، يصبح مدير المنتج والمعماري والمطوّر والمراجِع في آنٍ واحد، ثم يقيّم عمله بنفسه. حلّت الفرق البشرية ذلك بأدوار منفصلة ونقاط موافقة. ديوان يجلب هذا الهيكل إلى الوكلاء.

问题所在

AI 编程智能体很快，速度不是问题。问题在于：当你让一个智能体"把这个功能做出来"时，它同时充当产品经理、架构师、开发者和评审者，还给自己的工作打分。人类团队早已通过职责分离和审批节点解决了这个问题。Divan 把同样的结构带给智能体。

功能循环

  1. 关口 A——范围。 你批准功能卡片，包括被砍掉的部分。
  2. 关口 B——设计。 你批准方案，并从三个备选方案中选择一个。
  3. 关口 C——发布。 由你合并、部署和发布。智能体从不做这些事。

每个智能体都必须知道的三个事实

智能体团队的失败大多不是编码错误，而是某个智能体违反了以下事实之一——因为没人把它写下来。

1. 什么会触发生产环境部署？ 如果推送到 main 就会部署，那么智能体推送就等于发布。
2. 追踪策略是什么？ 它决定了成功如何衡量。对于承诺不做追踪的产品，Divan 绝不添加任何追踪。
3. 产品做过哪些公开承诺？ 安全智能体会逐条按名称核查每一次改动。

为什么叫"Divan"？

在历史上的波斯政府中，"迪万"指行政机构：由文书、财政、军籍等专业部门组成，每个部门把一件事做好，并共同向一位决策者负责。这正是这个团队的形态。
