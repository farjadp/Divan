# دیوان

**یک تیم محصول از ایجنت‌های هوش مصنوعی برای پروژه‌های نرم‌افزاری — ساخته‌شده حول یک انسان که تصمیم می‌گیرد.**

[English](README.md) · [روش (انگلیسی)](docs/method.md) · [تطبیق با پروژهٔ موجود (انگلیسی)](docs/adapting.md) · [نمونهٔ واقعی (انگلیسی)](docs/case-studies/taghvim.md)

> **وضعیت: مراحل اولیه (نسخهٔ ۰٫۱).** دیوان روی یک محصول زنده نصب و تطبیق داده شده است
> ([نمونهٔ واقعی](docs/case-studies/taghvim.md)). یک چرخهٔ کامل، از ایده تا انتشار، **هنوز** اجرا نشده است.
> وقتی اجرا شد، نتیجه‌اش، از جمله شکست‌ها، همین‌جا منتشر می‌شود.

## مسئله

ایجنت‌های کدنویس هوش مصنوعی سریع‌اند. مشکل سرعت نیست. مشکل این است که وقتی به یک ایجنت می‌گویی «این فیچر را بساز»، هم‌زمان مدیر محصول، معمار، برنامه‌نویس و بازبین می‌شود و **کار خودش را خودش نمره می‌دهد**. نتیجه: کد زیاد و سریع، که بخشی از آن مسئلهٔ اشتباه را حل می‌کند، قانونی را می‌شکند که کسی به ایجنت نگفته بود، یا مستقیم روی سایت اصلی منتشر می‌شود.

تیم‌های انسانی این مشکل را مدت‌ها پیش با **نقش‌های جدا و نقطه‌های تأیید** حل کرده‌اند. دیوان همین ساختار را برای ایجنت‌ها می‌آورد.

## دیوان چیست؟

کیتی آماده برای [Claude Code](https://docs.claude.com/en/docs/claude-code/overview) که یک ریپوی نرم‌افزاری را به یک سازمان تبدیل می‌کند:

| ایجنت | معادل انسانی | کد می‌نویسد؟ |
|---|---|---|
| `spec-writer` | مدیر محصول — تعریف فیچر | خیر |
| `architect` | مدیر فنی — طراحی، سه نسخهٔ پیشنهادی، شکستن کار | خیر |
| `builder` | برنامه‌نویس فول‌استک و موبایل، هر بار یک تسک | بله |
| `reviewer` | مهندس ارشد و QA — **مستقل** از سازنده | خیر |
| `security-checker` | امنیت و حریم خصوصی — قول‌های عمومی محصول را چک می‌کند | خیر |
| `feature-engineer` | مهندس یادگیری ماشین — **فقط اگر محصول مدل ML دارد** | فقط پوشهٔ ML |
| `release-docs` | DevOps و مستندساز — آماده می‌کند، هرگز منتشر نمی‌کند | فقط مستندات |

به‌علاوه:
- **`feature-loop`**: فرایندی که ایجنت‌ها را به هم وصل می‌کند، با **سه دروازه** که تصمیمش با توست.
- **`feature-definition`**: تبدیل درخواست‌ها به فیچرهای کوچک و قابل‌تست، با نشانهٔ موفقیت.
- **`divan-adapt`**: تطبیق کیت با یک پروژهٔ جاافتاده، **بدون شکستن قانون‌هایش**.
- **قفل کیفیت (hook)**: تا وقتی تست‌ها یا type-check خراب است، اجازهٔ تمام کردن کار را به ایجنت نمی‌دهد.
- **قانون‌های منع**: ایجنت نمی‌تواند push، tag یا انتشار کند و نمی‌تواند فایل `.env` یا کلیدهای امضا را بخواند.

## چرخهٔ کار

<div dir="ltr">

```
Idea ─► spec-writer ─► GATE A (you approve scope)
     ─► architect   ─► GATE B (you approve design, pick a variant)
     ─► builder × tasks ─► reviewer ⟲ (max 3 rounds) ─► security-checker
     ─► release-docs ─► GATE C (you merge, deploy, publish)
     ─► after release: success signal vs target → keep / iterate / remove
```

</div>

- **دروازهٔ A (محدوده):** تو کارت فیچر را تأیید می‌کنی، از جمله چیزهایی که حذف شده.
- **دروازهٔ B (طراحی):** تو روش را تأیید می‌کنی و برای تغییرات ظاهری، یکی از سه نسخه را انتخاب می‌کنی.
- **دروازهٔ C (انتشار):** تو merge، deploy و منتشر می‌کنی. ایجنت‌ها هرگز.

ایجنت‌ها اجرا می‌کنند. **تو** تصمیم می‌گیری چه ساخته شود، چه حذف شود و کی «به اندازهٔ کافی خوب» است.

## نصب

<div dir="ltr">

```bash
git clone --depth 1 https://github.com/farjadp/divan.git
./divan/install.sh /path/to/your/project
```

</div>

نصب‌کننده **هیچ فایلی را بازنویسی نمی‌کند**. اگر پروژه‌ات از قبل `CLAUDE.md` دارد، قالب دیوان کنارش با نام `CLAUDE.divan.md` نوشته می‌شود تا خودت ادغامش کنی. اگر `.gitignore` پوشهٔ `.claude/` را پنهان کرده باشد یا پروژه از قبل دستورالعمل ایجنت داشته باشد (مثل `AGENTS.md`)، هشدار می‌دهد. با `--dry-run` می‌بینی چه کاری می‌کند، بدون اینکه چیزی عوض شود.

بعد از نصب:

۱. `CLAUDE.md` را پر کن؛ مهم‌تر از همه **بخش ۲** (سه واقعیت پایین) و **بخش ۴** (دستورهای واقعی پروژه).
۲. پروژه را در Claude Code باز کن و `/agents` را بزن تا تیم را ببینی.
۳. **پروژهٔ موجود است؟** بگو: *«adapt Divan to this repo»*.
۴. بگو: *«run the feature loop for: یک فیچر کوچک و واقعی»*.

## سه واقعیتی که هر ایجنت باید بداند

بیشتر شکست‌های تیم‌های ایجنتی، اشتباه کدنویسی نیستند. ایجنتی یکی از این سه را شکسته، چون کسی آن را ننوشته بود:

۱. **چه چیزی باعث انتشار روی سایت اصلی می‌شود؟** اگر push روی `main` یعنی انتشار، پس push کردن ایجنت یعنی انتشار.
۲. **سیاست ردیابی چیست؟** این تعیین می‌کند موفقیت چطور سنجیده شود. دیوان هرگز به محصولی که قول «بدون ردیابی» داده، ردیاب اضافه نمی‌کند.
۳. **محصول چه قول‌هایی عمومی داده است؟** (مثلاً «هیچ درخواستی به سرویس ثالث نمی‌رود» یا «آفلاین کار می‌کند».) ایجنت امنیت، هر تغییر را با تک‌تک این قول‌ها چک می‌کند.

## «تعریف فیچر» با «Feature Engineering» فرق دارد

**Feature Engineering** اصطلاحی از یادگیری ماشین است: ساختن متغیرهای ورودی‌ای که مدل از آن‌ها یاد می‌گیرد. تبدیل نیاز کاربر به فیچر محصول، **تعریف فیچر (Feature Definition)** نام دارد و بخشی از مهندسی نیازمندی‌هاست. دیوان این دو را جدا نگه می‌دارد: ایجنت‌های جدا و اصطلاح‌های جدا.

## چرا «دیوان»؟

در حکومت‌های تاریخی ایران، «دیوان» همان دستگاه اداری بود: واحدهای تخصصی مثل دیوان رسائل (مکاتبات)، دیوان استیفا (مالی) و دیوان عرض (لشکر). هر واحد یک کار را خوب انجام می‌داد و همه به یک تصمیم‌گیرنده پاسخ می‌دادند. این تیم هم همین شکل را دارد.

## محدودیت‌ها، صادقانه

- **کشف نیاز کاربر با توست.** ایجنت نمی‌تواند با کاربر مصاحبه کند. به آن شواهد واقعی بده یا ادعاها را «فرض» علامت بزن.
- **سلیقه با توست.** ایجنت‌ها طراحی قابل‌قبول می‌سازند، به‌ندرت طراحی عالی.
- **حساب‌ها با توست.** استورها، پرداخت، کلیدهای امضا و مسائل حقوقی فقط کار انسان است.
- **سرعت، بدهی فنی را پنهان می‌کند.** اگر نمی‌توانی یک ماژول را در دو دقیقه توضیح بدهی، بایست و بازبینی کن.
- **هزینه.** اجرای طولانی ایجنت‌ها توکن زیادی مصرف می‌کند. تسک‌های کوچک ارزان‌ترند و نتیجهٔ بهتری هم می‌دهند.
- **ابزارها تغییر می‌کنند.** قالب ایجنت‌ها و مهارت‌ها و hookها تغییر می‌کند؛ با [مستندات به‌روز Claude Code](https://docs.claude.com/en/docs/claude-code/overview) چک کن.
